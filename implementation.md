# Pilates Workout Generator: Implementation Plan

## Stack Summary

- **Frontend:** React + React Router + CSS/Tailwind[cite: 1]
- **Backend:** Node.js on Azure Functions (HTTP-triggered)[cite: 1]
- **Database:** Azure Cosmos DB (free tier)[cite: 1]
- **Hosting & Deploy:** Azure Static Web Apps via GitHub Actions[cite: 1]
- **Repo:** GitHub[cite: 1]

---

## Phase 0: Infrastructure and Azure Setup (1–2 hours)

Do this first. Everything else depends on it.[cite: 1]

| Task | What to do | Model / tool |
|---|---|---|
| 0.1 Create Azure resources | Set up Cosmos DB account + database + container (`exercises`) in the Azure portal. Create an Azure Static Web App instance and link your GitHub repo. | Do this manually in the portal. It's faster than scripting for a one-time setup.[cite: 1] |
| 0.2 Scaffold the project | Monorepo with `/client` (React via Vite) and `/api` (Azure Functions). Set up package.json files, install dependencies, wire up a hello-world route and confirm local dev works. | **Gemini 1.5 Flash** in Antigravity. Fast scaffolding task, doesn't need deep reasoning.[cite: 1] |
| 0.3 Configure connections | Get the Cosmos DB connection string into your Azure Function local settings. Ensure the Static Web App config routes `/api` calls to your function backend. Test that your local function can read/write a test document to Cosmos. | **Gemini 1.5 Flash** in Antigravity for the config files. Do the portal settings yourself.[cite: 1] |
| 0.4 Set up GitHub Actions deploy | Confirm the automated GitHub Actions workflow generated by Azure Static Web Apps successfully builds and deploys both the React app and the Azure Functions. | Manual. Monitor the Actions tab in GitHub.[cite: 1] |

**Gate:** You should be able to hit your deployed Azure Function from your deployed React app before you move on.[cite: 1]

## Phase 1: Backend Core (3–4 hours)

These two tracks can run in parallel sessions.[cite: 1]

### Track A: Database and API

| Task | What to do | Model / tool |
|---|---|---|
| 1A.1 Define data models | Write the JSON document schema for exercises. Needs: id, name, muscleGroup, difficulty (1-3), equipment (mat/bands/ball/none), duration, instructions. | **Gemini 1.5 Flash** in Antigravity. Straightforward schema work.[cite: 1] |
| 1A.2 Build fetch route | Express/Function route for `GET /api/exercises`. Use the Cosmos DB Node.js SDK (@azure/cosmos). | **Gemini 1.5 Flash** in Antigravity. Bread-and-butter API work.[cite: 1] |
| 1A.3 Seed the database | Write a seed script that populates Cosmos with 35–45 exercises covering all combinations of equipment, focus, and difficulty to ensure the algorithm has enough candidates. | **Gemini 1.5 Flash** in Antigravity. Give it your schema and tell it to generate varied, realistic data.[cite: 1] |

### Track B: Matching Engine (Azure Function)

| Task | What to do | Model / tool |
|---|---|---|
| 1B.1 Design the scoring algorithm | Define the filtering and selection logic. Filter by user equipment and focus. Score candidates to prevent consecutive identical muscle groups, ramp up difficulty then cool down, and balance overall muscle representation. | **Gemini 1.5 Pro** in Antigravity. This is the most important logic in your project. Use the stronger model to think through edge cases.[cite: 1] |
| 1B.2 Build the Azure Function | HTTP-triggered `POST /api/generate-routine` function that takes focus, equipment, and duration. It fetches the exercise bank, runs the scoring algorithm in a greedy loop until the duration is filled, and returns the sequence. | **Gemini 1.5 Flash** in Antigravity once the algorithm is designed. The Function wrapper is boilerplate.[cite: 1] |
| 1B.3 Test locally | Use Azure Functions Core Tools to run the function locally. Hit it with test parameters and confirm the resulting routine flow makes sense. | Manual testing. Adjust weights as needed.[cite: 1] |

**Gate:** Your API can fetch exercises, and your Azure Function returns a logically scored, time-bound workout sequence. Both work locally and deployed.[cite: 1]

## What to Cut If You're Running Out of Time

Cut in this order (least important first):[cite: 1]

1. Dynamic visual difficulty arc on the overview (just use text difficulty labels)
2. Simulated progressive loading steps on the generator screen (use a standard spinner)
3. Advanced media in the active player (use typographic placeholders instead of images/video)
4. Responsive mobile styling (if demoing strictly on desktop)

Do not cut: the parameter selection wizard, the algorithm logic, or the final routine overview. Those are the elements that prove your system works.
